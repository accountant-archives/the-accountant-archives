# The Accountant Archives

An open, collaborative archive for the 800-film Accountant saga: read canon, write a film’s story, challenge the established account, and let the community decide what remains canonical.

The interface is intentionally built as a product rather than a content site: a full chronological archive, an eras graph, a contextual writing desk, revision history, canon challenges, moderation controls, and an accountant-flavoured reputation system named **Ledger Balance**.

## What is included

- All 800 films are preloaded in the database.
  - Movies 1–30 are debt-chasing entries.
  - Movies 31–40 are final notices.
  - The fraction countdown is generated by `accountant_film_title()` rather than manually hard-coded.
  - Movies 220–300 are the editable Grothkin Lore era.
  - Movie 800 is `Paid In Full`.
- Google login with Supabase Auth; guests can browse without signing in.
- Row Level Security on every exposed data table, with direct table grants declared explicitly.
- Draft autosave, live word/read-time indicators, Markdown editing, preview, and revision capture.
- One canon story per film, challenger voting with one vote per member, 7-day challenge windows, and permanent archiving of losing stories.
- Up/down story reactions, bookmarks, comments, reports, member notifications, and the Ledger Balance reputation score.
- Writer, moderator, and administrator roles. The admin control room edits eras, approving, rejecting, or archiving submissions.
- A locked-down scheduled Edge Function for automatic expiry resolution of canon challenges.
- GitHub Pages deployment workflow.

## Local run

```bash
cp .env.example .env.local
npm install
npm run dev
```

Set these values in `.env.local` from Supabase Dashboard → **Connect**:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_KEY
```

Only a publishable key belongs in the browser. Never put a Supabase secret/service-role key in `VITE_*` variables.

## Supabase production setup

The complete schema is in [the initial migration](supabase/migrations/20260803074234_initial_accountant_archives.sql). It creates the data model, policies, generated catalogue, and supported database routines.

1. Apply the migration to the intended Supabase project.
2. In **Authentication → Providers**, enable Google and add the Google OAuth client ID and secret.
3. In **Authentication → URL Configuration**, add both the local URL and the GitHub Pages URL to the redirect allow-list. Google’s authorised redirect URI is:

   ```text
   https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback
   ```

4. Sign in once with the Google account that should control the archive. Then, in Supabase SQL Editor, find that account and promote it:

   ```sql
   select id, email from auth.users order by created_at desc;

   insert into public.user_roles (user_id, role)
   values ('PASTE_THE_ADMIN_AUTH_USER_UUID', 'admin')
   on conflict (user_id) do update
     set role = excluded.role, assigned_at = now();
   ```

   This is the deliberately small, auditable “special sign-in” step: administrator authority is stored server-side, not inferred from an editable client field or email address.

5. Deploy the challenge resolver and give it a non-guessable secret:

   ```bash
   supabase functions deploy resolve-challenges
   supabase secrets set CHALLENGE_CRON_SECRET='a-long-random-value'
   ```

6. Schedule a call every 30 minutes. In the SQL below, put the function URL and matching secret into Supabase Vault first; it keeps them out of the database source and cron job text.

   ```sql
   select vault.create_secret('https://YOUR_PROJECT_REF.supabase.co', 'accountant_project_url');
   select vault.create_secret('a-long-random-value', 'accountant_challenge_cron_secret');

   select cron.schedule(
     'resolve-accountant-challenges',
     '*/30 * * * *',
     $$
       select net.http_post(
         url := (select decrypted_secret from vault.decrypted_secrets where name = 'accountant_project_url') || '/functions/v1/resolve-challenges',
         headers := jsonb_build_object(
           'Content-Type', 'application/json',
           'x-cron-secret', (select decrypted_secret from vault.decrypted_secrets where name = 'accountant_challenge_cron_secret')
         ),
         body := '{}'::jsonb
       );
     $$
   );
   ```

   Tied challenges preserve existing canon; a replacement needs a clear vote lead. The Edge Function has JWT verification disabled only because it requires the separate, server-only `x-cron-secret` header before it can access the service-role client.

## GitHub Pages deployment

1. Create a GitHub repository named `the-accountant-archives` and push this project’s `main` branch.
2. In the repository **Settings → Pages**, set the source to **GitHub Actions**.
3. Add these Actions secrets:

   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_PUBLISHABLE_KEY`

4. Push to `main`; [the workflow](.github/workflows/deploy-pages.yml) builds and deploys the static React app.

The Pages app is intentionally static. Authentication, permissions, voting, data, and challenge resolution are handled by Supabase, so no server secret is ever shipped to GitHub Pages.

## Data model notes

The database contains the following collaboration primitives:

- `eras`, `films`
- `profiles`, `user_roles`, `site_settings`
- `stories`, `story_revisions`, `story_metrics`, `story_reactions`, `bookmarks`
- `comments`, `comment_reactions`
- `canon_challenges`, `challenge_votes`, `challenge_metrics`
- `reports`, `moderation_actions`, `notifications`

All tables in `public` have RLS enabled. Permission helpers and privileged triggers live in a non-exposed `private` schema. The service-only resolver function has its execute privilege granted only to `service_role`.
